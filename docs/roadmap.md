# Remote Agent Bridge：现状评审与实施路线图

**评审日期：2026-11-22 · 起始基线：`e80d913` 加当时的未提交改动 · 第 2 节区分已验证与待办**

本文面向下一轮开发。现状以源码和本轮实际测试为准，而不是把根目录的本地规划草稿当成产品说明。旧草稿中的外置 Gateway、公开网络部署、GUI 执行器和多设备是候选方向，不是本轮交付承诺。

## 1. 结论与产品边界

RAB 已经走通「电脑启动 → 手机注册/登录 → 本机签发配对码 → Agent 认证重连 → 会话/任务 → 手机收结果」。下一版的首要目标不是增加执行能力，而是让这条链路在**断网、关页、重启、撤销、超时和磁盘写入失败**时仍能给出正确结果。特别要区分「请求已记录」「Agent 已接收」「执行已结束」「已确认停止」和「结果未知」。

| 决策 | 下一版推荐默认值 | 改变该决策的条件 |
|---|---|---|
| 产品范围 | 单操作者、单台电脑、同机部署 Gateway 与 Agent；可有多个 Provider | 连续稳定试用后确有多设备需求，且设备归属和执行路由已通过独立验收 |
| 网络范围 | localhost 与用户控制的私网优先；手机端需要安全上下文时提供私网 HTTPS | 公网部署是独立产品决策，不因配好一个 HTTPS URL 就默认开启 |
| 默认能力 | 先交付只读、后台、可停止的任务；不操作用户当前桌面 | 能力有明确权限、已验证的隔离边界和取消契约，才讨论开放 |
| 安全原则 | 设备身份不等于用户授权；文本风险提示不等于权限；超时不等于已经清理 | 不降低这三项要求换取接入速度 |
| 架构取舍 | 保留 pnpm、TypeScript、Fastify 和单实例；先加明确模块接口，不做框架重写 | 前端组件维护成本、存储事务或多实例需求有可测证据时再升级 |
| 分发方式 | 保留命令入口、不开机自启；不恢复未签名托盘程序 | 有签名、安装/卸载、明确选择加入和维护预算之后再评价常驻包装 |

## 3. 实施前分模块评审

| 模块 / 阅读入口 | 现状 | 最需要解决的问题 → 对应工作项 |
|---|---|---|
| Gateway HTTP / WS：`apps/gateway/src/index.ts`、`app.ts`、`agent-slot.ts` | Fastify 进程内单例，路由通过导入注册；单槽位；会话命令按 `request_id` 关联 | 把存活、已握手、已配对、当前代连接和操作者授权分开。旧连接关闭只能清理自己的命令；事件必须来自当前绑定连接并对应指定任务/会话。接入校验、握手截止、心跳和资源上限 → `G01`、`G02`、`T01` |
| 账号 / 设备：`routes/auth.ts`、`routes/devices.ts`、`security.ts`、`pairing.ts`、`device-keys.ts` | scrypt 密码、随机 Bearer 哈希、登录/配对按 IP 限流、Ed25519 一次性挑战和旧 token 迁移 | 全局单槽位与多账号 API 不应混用成隐式授权；普通请求逐用户做同步 scrypt；尚无服务端注销和到期。配对码与连接代、公钥、授权版本绑定；普通新绑定不签发旧凭证 → `G01`、`G02`、`A01` |
| 任务 / 会话：`routes/tasks.ts`、`routes/sessions.ts`、`task-risk.ts` | 提交幂等、会话历史、关键词风险提示、待确认/拒绝/到期、最近任务列表 | 持久化在发送之后；确认后缺明确过渡状态；事件写入缺严格迁移和关联；删除会话、撤销设备、断线时缺统一语义。补提交回执、单调状态、取消、任务/会话对账 → `T01`–`T03` |
| Agent / 进程：`services/agent/src/index.ts`、`process-control.ts`、`task-timeouts.ts`、`identity.ts` | 固定间隔重连、内存单队列、两类超时、Ed25519 私钥本地保存 | 离线结果没有回放；队列无明确上限；总预算未覆盖前置会话初始化；取消结果未证实，外部没有通用取消入口。先修进程生命周期，再做重连、闸门、停机 → `R01`、`R02`、`T02`、`T03` |
| Local Provider：`adapters/local.ts` | 时间、系统/进程信息、工作区目录/文本读取；内存会话 | 当前路径检查是词法比较，不足以保证实际文件仍在工作区；读取在截断前会读完整文件。明确允许目录、实际路径与保留敏感目录，限制文件类型/大小、读取时长和并发 → `P01` |
| HTTP Provider：`adapters/http.ts` | 适配会话、发消息、取消接口；结果一次返回 | 前置会话请求和取消请求缺明确截止；本地 fetch 停止与对端真正停止不同；需限制响应体、校验回包、区分不可取消和结果未知。仅允许本机操作者配置已信任的端点 → `P02`、`T02` |
| Codex / WorkBuddy：`adapters/codex.ts`、`adapters/workbuddy.ts`、`apps/gateway/src/discovery.ts` | 两个无头 CLI；本地保存外部线程/会话映射；Codex 能回传结构化动作；WorkBuddy 有安装版本兼容逻辑 | 启动、恢复、权限、进程清理、输出解析要有共同契约；记忆映射按 Provider 实例隔离；保守校验 CLI 版本，默认不给宽权限。WorkBuddy 的结果不能被宣传成和 Codex 同样具备动作轨迹 → `P02`、`P03` |
| 协议 / SDK：`packages/protocol/src/index.ts`、`packages/adapter-sdk/src/index.ts` | TypeScript 类型与 `envelope`，统一 Provider 接口 | 类型断言不是输入校验。建立运行时 schema、稳定错误/状态、确认/回执/停止语义、兼容矩阵；传输类型预留不等于已支持 → `G02`、`T01`、`P02` |
| 状态 / 配置：`apps/gateway/src/state.ts`、`packages/config/src/index.ts` | JSON 快照原子替换、任务清理与旧数据兼容；数据根共享；环境变量可覆盖部分路径 | 同步整文件落盘无事务，损坏读取可能静默进入空或部分状态；200 条是快照上限，不是全局内存/活跃量限制。先定义数据业务接口和故障语义，再做可回滚 SQLite 迁移 → `D01`、`D02` |
| 手机 Web：`apps/web/index.html` | `sessionStorage` 登录凭据、`localStorage` 待处理 ID、定时请求、确认卡片、动作详情 | 丢响应后没有稳定重试入口；等待中和运行中的展示不足；切换会话有异步抢写风险，结果详情不能可靠从历史恢复；配对完成需刷新 Provider/会话可用性。手机应以服务端时间线为准 → `W01`、`W02` |
| 配置页 / 部署：`apps/web/setup.html`、`scripts/rab.ps1`、`routes/setup.ts`、`routes/pages.ts` | 本机管理 token、发现 Provider、Windows 隐藏启动与状态查询 | 脚本仍硬编码 `8787`/`.rab`，部分存活会被视作已运行，启动用固定等待；页面路径依赖启动目录；配置页残留托盘文案；不把 HTTPS URL 的格式检查误当真正 TLS 执行 → `O01`、`O02`、`A02` |
| 测试 / 文档：`.github/workflows/ci.yml`、各模块 `tests`、`README.md`、`docs/` | 真实 Gateway 集成、Agent 进程测试、Web 语法检查，部分测试辅助函数重复 | 缺少真实浏览器 E2E、稳定故障注入、发布/迁移验证；文档中的「未绑定无任何消息」「树已清理」「支持取消」需分别陈述控制帧、清理验证和用户入口 → `Q01`、`Q02` |

## 4. 里程碑、排序与人日

本轮按以下顺序实施私网稳定版的核心路径，不改现有部署、不扩大远程执行权限：

1. **只读边界**：验证真实文件路径；拒绝链接、保留目录和敏感凭据；给读取和目录结果设限。
2. **任务可靠性**：先持久化再派发；同键重试不重复执行；对账只询问状态、不重发任务；手机可取消，无法证明停止时明确标记结果未知。
3. **手机体验**：首次配对、切换会话、任务状态和恢复由服务端记录驱动；发送响应丢失时保留同键重试，不自动重发。
4. **发布验收**：验证进程与网络中断、落盘失败、重复任务和跨账户权限；更新部署说明。未跑的多平台、真机、迁移和第三方 Provider 验收仍是发布门槛。

以下为单开发者净开发估算，包含对应用例和文档更新，不含等待外部软件、签名证书或真实用户反馈。按发布门槛推进，不按日历硬发。P0 阻止放宽使用范围；P1 是下一稳定版核心；P2 取决于主流程稳定；P3 不承诺。

| 里程碑 | 顺序与预计人日 | 交付物 | 出口条件 |
|---|---:|---|---|
| M0：收敛当前基线 | 第一阶段，4–7 | `R01 G01 G02 P01 Q01` 的 P0 部分；区分已实现、测试通过和暂不可用 | 进程清理被验证或相关 Provider 被明确禁用；设备归属、只读路径与事件隔离有回归；发布资料不夸大保证 |
| M1：可靠任务闭环 | M0 后，8–12 | `D01 T01 T02 T03 R02 P02 W01`；状态/回执、取消、断线恢复、受限队列 | 掉线不重复执行；取消只有在停止得到验证时才显示成功；结果未知有明确提示；两端及手机能恢复一致状态 |
| M2：可信私网试用 | M1 后，6–10 | `A01 A02 W02 O01 O02 Q02`；可用的账号会话、Windows 运维、可复现的移动端流程 | 一次完整安装演练；Windows/Ubuntu CI 通过；真机配对、发任务、刷新、撤销和重新配对通过；管理凭据不进入常规日志 |
| M3：可维护发布 | M2 后，8–12 | `D02 P03 Q03`；SQLite 迁移、备份恢复、Provider 合约、审计与发布手册 | 旧数据迁移、升级中断、回退演练和兼容性矩阵通过；受支持的能力有用户可理解的边界 |
| M4：按需求扩展 | 无固定排期 | SSE 或附件、可选 PWA、多设备、独立运行环境等按验证价值排队 | 不回退授权、隐私与非干扰约束；不把实验功能默认启用 |

主依赖：`R01 → T02/R02`；`G01/G02 → T01 → T03 → W01`；`D01 → T01 → D02`；`A01/A02 + O01 → Q02`；`P02 → P03`。可并行准备测试夹具、文档勘误、前端纯状态组件和配置校验，但先冻结共享状态/错误契约，再并入端到端逻辑。

### M1 · 任务闭环、状态机与 Provider 契约

| ID | 工作与设计选择 | 验收 |
|---|---|---|
| `D01` 存储接口先行 | 收束路由对全局 Map 的直接修改，先抽任务/消息/设备仓储和事务语义；加载时全量验证后发布快照；损坏数据显式进入维护状态，保留文件和可恢复备份。把上限按总字节、活跃任务、终态窗口和分页分别定义。 | 磁盘写入失败不返回「已接受」，也不把未记录任务发给 Agent；损坏文件不会被空数据覆盖；在途任务不被历史裁剪挤掉。 |
| `T01` 幂等与任务状态 | 按操作者和请求键去重，并记录输入摘要、会话、Provider、绑定设备及授权版本。相同键相同请求返回原任务，不同输入有明确冲突。以状态机管控确认、调度、回执和终态；同一事件不重复写会话，输入和结果各只追加一次。确认绑定待执行内容、设备及策略版本，失效后重审或取消。 | 双击、请求重试和并发确认/拒绝均可预测；会话删除、撤销、过期时不能派发待确认任务；重复和乱序事件不污染线程或覆盖终态。 |
| `T02` 取消与截止时间 | Agent 为每个任务提供取消信号；排队取消直接移出；运行取消带 `cancel_requested` 或等价状态，待 Runner 确认后出终态。覆盖初始化、执行和清理各阶段的预算；取消重复调用幂等。撤销操作要先阻断新增任务，并使未执行旧任务失效；把已执行副作用与「已经停止」分开。 | 排队取消零执行；运行取消等待清理结果；临界竞态只产生一个终态；远端取消不可证实时可明确区分，不能显示「未执行」。 |
| `T03` 回执与断线恢复 | Gateway 先落盘，再派发；Agent 记录任务键/尝试与未回传事件，补 `task.accepted` 或等价回执、事件序号与有界回放。短暂掉线只补发结果或同键回执，不自动重跑有副作用任务；Agent 彻底丢失执行证据时标记 `outcome_unknown`，由用户决定是否重新提交。 | 覆盖落盘后发送前、收到任务后回执前、真正开始后结果前、结果后浏览器收到前四个断点。旧连接或旧尝试上报不会导致二次执行或二次追加。 |
| `R02` Agent 调度、连接与停机 | 将连接与握手、任务队列、执行器、事件回放从入口拆开；为控制帧与任务帧建明确状态，限制每个操作者和 Provider 的队列，遵守背压。连接使用带抖动的退避；同机配置和凭据变化支持可诊断的重新加载；停机先阻止接单，再收尾。 | 半开、网络抖动、Gateway 重启和 Agent 停机有有界等待；队列满有可重试错误及明确提示；清理未证实不启动下一个 Provider 任务。 |
| `P02` 统一 Adapter 合约 | SDK 增加取消信号、阶段进度/活动、严格输出预算与失败类别。HTTP 的连接、会话、取消响应分别有 deadline；将本地取消与远端状态确认分开。CLI 使用安全参数边界，验证执行和恢复两条路径都保有预期沙箱/工作区；不给不必要的环境、凭据和文件访问。 | 四个 Adapter 用同一套合约用例验证支持模式、超时、取消、会话恢复、超大输出和错误；不能提供可靠隔离、取消或兼容验证的配置禁用或明确降级。 |
| `W01` 服务端驱动任务页面 | 建立 API 错误层、会话视图状态和可恢复的提交草稿；请求前登记稳定键，网络超时保留输入并用同键重试；任务卡显示待确认、排队、运行、取消中、结束、结果未知。按会话拉取服务器时间线并按任务/事件 ID 去重；单飞请求、可见性预算、请求回执与会话切换代数保护。 | 刷新、锁屏恢复、账号切换、两标签页并行、快速切换会话、请求已到服务端但响应丢失均不串会话、不漏确认、不重复提交。 |

建议状态语义：`awaiting_confirmation → dispatch_pending → queued → running → succeeded/failed/cancelled`。`cancel_requested` 适用于已接单但尚未确认停下；`outcome_unknown` 代表系统无法证明最终结果，不应自动重跑。`dispatch_pending` 是 Gateway 承诺有记录，不代表已送达；排队取消可直接到 `cancelled`。每次状态变化记录来源、时间、尝试和序号；后续若补到可验证结果，应通过明确的对账事件修正未知状态，不能默许任意回退。拒绝确认只表示本任务尚未派发；运行中取消不会回滚已发生的副作用。

## 6. 两项容易做错的设计

### 6.1 「确认」不是执行沙箱

已有正则适合当提醒，不知道 Provider 最终会执行什么，也不能从自然语言准确证明「低风险」。建议把权限模型拆成三层：本机操作者选择 Provider 与允许工作区；Agent 对结构化、可限制的能力做判定；如需批准，手机只批准具体能力、作用范围、任务、设备和有效期。超出批准范围时拒绝或重新询问。对无法在执行时保证这些约束的外部 Provider，默认只读、禁用不受控能力，或者明确标记为仅限本地配置的实验功能。对新版本、恢复旧会话和策略更新都做同样的检查。

### 6.2 「可靠」不等于宣称恰好执行一次

分布式链路无法从 HTTP 超时判断任务到底有没有执行。产品契约应该是：在声明的幂等窗口内，不自动重复发起同一个执行意图；如果失去执行证明，显示结果未知并保留证据。即使持久队列落地，也不以「重新发一遍」修复丢回执；自动延迟重试只用于明确未执行、同键去重或安全的只读操作。

## 7. 验收剧本与建议指标

| 剧本 | 自动化或实机 | 通过标准 |
|---|---|---|
| 首次上手 | 真实 Agent + 手机浏览器 | 使用受支持网络，从启动到首个只读任务不需要重启或手动改 URL；记录实际耗时，不承诺未经测量的秒数 |
| 并发或乱序 | 固定时钟 + 集成测试 | 并行提交、确认/拒绝、断连重连、旧连接关闭、序号重复/乱序，不出现多派发、越权写入或状态回退 |
| 撤销与换绑 | 集成 + 真实 Agent | 旧连接和授权不能接到新任务；原在途动作如无法确认停止，手机如实显示；换绑需要本机操作，旧账归属不漂移 |
| 超时/取消/关闭电脑 | Windows 与 POSIX 真实进程夹具 | 在目标清理预算内停止整棵**受管**进程树，超预算时进入隔离/未知，不开下一任务；不对所有第三方远端进程作同样承诺 |
| 断线、手机后台、刷新 | 浏览器 E2E + 真实手机 | 服务端记录不丢；重新前台后能看到待确认与最新状态；不重复渲染结果或触发任务 |
| 落盘与升级 | 故障注入 + 双数据目录演练 | 文件只读、磁盘写入失败、损坏快照、旧格式迁移、中途失败、恢复旧版本均有明确结果，保留恢复材料 |
| 保密与限额 | 集成 + 脱敏诊断检查 | 密钥不进 HTML、常规 URL 或日志；跨账号数据不泄露；超出并发、消息、输出、队列和历史预算均可解释 |

建议先量基线，再定正式指标。首轮预算候选：每设备 1 个运行、最多 20 个排队，明确区分排队期限和执行期限；普通 LAN 下 95% 的状态变化在 3 秒内可见（不含 Provider 执行耗时）；清理验证期限初始 10 秒，实测后调整。发布版只把「零重复派发」「零越权写入」「零假报已停止」当硬性不变量，而不是把良好延迟当安全证据。资源和时限使用可配置上限，UI 展示退避或排满原因，审计只保留最小字段。

## 9. 第一个迭代怎么开工

1. **第一天：`R01` 优先。** 将三个现有失败的分类从输出文字落实到可观察的退出情况和测试夹具生命周期；在可复核的 Windows 路径上验证，不能确认清理就暂停任务队列。README 同步降低承诺，不把红测标绿。
2. **第二批：`G01` 和 `G02`。** 统一「操作者 → 当前已认证且已绑定设备 → 指定会话/任务」的授权决策，固定连接代和状态回报码；保留 Ed25519 正常绑定与旧凭据迁移的现有正向测试。
3. **第三批：`P01` 和 `Q01`。** 收紧 Local 只读范围，回归用例覆盖实际路径、安全输出和关键授权；把「已实现」「已测试」「仅规划」分类写入发布说明。
4. **再进入 `D01`、`T01`、`T02`。** 在改界面与存储技术之前，把任务状态、取消、已确认停止与结果未知定成两端共用契约。评审切分建议：进程清理、授权/连接、状态/持久化、取消/恢复、手机/运维各自独立。

**第一版可交付定义：手机点一次能准确知道电脑是否接单、是否正在跑、能否停止和结果是什么；如果系统不知道，它明确说不知道。**

## 10. 下一轮实施顺序

1. **先做本机安装运维 `O01 / O02`。** 统一实际端口/目录解析；消除「只启动一半却显示正常」；实现可验证的启动、受控停止与失败恢复。用独立数据目录跑默认/自定义端口、端口冲突、半故障、停机中有任务、目录带中文五个场景。
2. **再做账号与私网入口 `A01 / A02`。** 本机所有者引导、服务端注销与过期、限制管理与 Agent 路由、实际检查 TLS。已登录的无权账号不得访问绑定状态或派发任务；账号过期后刷新不能读出历史。
3. **随后做试用验收 `Q02 / P03`。** 真实 Agent 冒烟已加入 CI 配置，但还需实际跑完平台矩阵；再在受控夹具与私网真机做两种移动浏览器及支持的 Provider 验收。不合格的 Provider 不纳入稳定版支持范围。
4. **最后做迁移和发布 `D02 / Q03`。** 先用脱敏夹具演练一致性、备份与回退，再增量迁移到 SQLite；补脱敏诊断、审计和发布说明。达到这些门槛后再评估扩大使用范围。
